# GUI・ハッカソンデモ設計

状態: **体験の提案 / 未実装**。目的は「チェーン上の入力が、稼働中の Agent の行動を変えた」と目で追えること。

## 画面構成

| 領域 | 内容 |
| --- | --- |
| メインの観察フィールド | 24体を初期案とする個体群。移動、短い軌跡、活性に応じた発光、行動アイコン |
| Agent 選択パネル | agentId、名前、モデル種別・版、owner、稼働状況、適用 revision |
| Status 操作パネル | Rest / Explore / Forage、energy、stimulus、ウォレット送信ボタン |
| イベント帯 | 送信 → ブロック取込 → ログ受信 → Agent 適用 → 確認深度到達 |
| 詳細欄 | Tx hash、block、eventId、入力 Status、行動変化、Runtime tick |

メイン領域を広く取り、個体の動きで第一印象を作る。デモモデル使用時は `Demo model`、MaleCNS の回路使用時はそのモデル名を表示する。エラーや停止もラベルで分かるようにする。

## 見せる動き

| 入力 | デモモデルでの初期表現案 |
| --- | --- |
| Rest | 速度を下げ、周囲で小さく動く |
| Explore | 領域内を探索し、軌跡が広がる |
| Forage | 共有の餌ポイントへ向かう傾向が増える |
| 高い energy | 活動できる時間・速度の上限が増える |
| 高い stimulus | 旋回や活性の応答が強くなる |

上記はルールベースのデモモデルに対するマッピング案で、生物学的性質の主張ではない。MaleCNS モデルに差し替える際は、回路が実際に出力した行動に対応させる。

各個体の seed と内部状態を異ならせることで、同じ条件でも全員が同時に同じ動きをする見た目を避ける。GUI は Runtime 由来の座標を補間する。GUI 独自の乱数で行動を生成しない。発光・軌跡などの演出は行動計算と区別する。

## デモの流れ（約60〜90秒の想定）

1. 事前登録・起動した24体がフィールド内で動いている。1体を選ぶと現在のチェーン Status と Runtime 状態が見える。
2. 選んだ個体を `Rest` から `Explore`、高い刺激に変更してウォレットで送信する。
3. 送信中は操作パネルの進捗だけ更新する。ブロックに取り込まれてログを受信すると該当個体に受信リングを表示する。
4. Runtime が入力を適用したら、個体の移動範囲と活性表示が変わる。詳細欄に原因 Tx と適用 revision を表示する。
5. 別の個体に `Forage` を設定し、同じフィールド内で異なる振る舞いを比較する。
6. 最後に履歴を開き、チェーンのイベントと行動変化の対応を示す。

1件の更新は対応する1個体を変える。周囲の個体はそれぞれの状態で動き続ける。全員への一括更新は v0.1 の必須機能に含めず、必要なら owner のみが操作できる上限付き batch API を次の設計で追加する。

## 接続や処理が遅れた場合

- ウォレット拒否・Tx revert：Status 適用済みにせず、入力値を残して理由を表示する。
- ブロック待ち：待機時間を表示する。未取込の入力で行動を先行変更しない。
- Runtime 停止：「チェーン保存済み / Agent 未適用」と表示する。
- stream 停止：最後のフレームを短時間補間した後停止し、「再接続中」を表示する。
- reorg：取り消されたイベントと軌跡を撤回し、再生後の snapshot に差し替える。
- オフライン再生：明示的な Replay モードとし、Live chain と同じ表示にしない。

## 実装の受入条件

1. **登録**: 1 Tx で Registered と初期 StatusUpdated が順に発火し、画面に1個体として現れる。対応 Runtime が未起動なら offline を表示する。
2. **更新**: owner の Status 更新がログから処理され、対象個体の appliedRevision と動きが変わる。他の個体の Status は変わらない。
3. **因果の追跡**: 表示された動きから入力イベント・Tx・モデル版・適用 tick を確認できる。
4. **再配送**: 同じログを複数回取得しても同じ revision を再刺激しない。
5. **再起動**: Runtime と Backend を再起動後、履歴と checkpoint から入力欠落なく復旧する。
6. **拒否**: 非 owner・不正値・古い expectedRevision は拒否され、正常イベントも行動変更も発生しない。
7. **競合・再編成**: 順番違いの配送、取り消されたログ、再取込の経路をローカルチェーンで検証する。
8. **GUI 再接続**: リロードと SSE 切断後も snapshot と後続イベントの境界で入力を欠落しない。
9. **見栄えと証拠**: 実ブラウザーで24体の連続動作と2体以上の Status 更新を確認し、Tx と反応が同時に見える動画を記録する。

測定は Tx 送信→取込 と、ログ受信→Runtime 適用→画面表示を分ける。後者はローカル環境で p95 500ms 以下を初期目標とし、計測結果とともに調整する。チェーンの取込時間をこの値に含めない。
